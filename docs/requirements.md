# Unified Student Placement System (USPS) – Requirements for the two PBL modules

Source: the IEEE SRS of the Unified System for Student Placement in Academic Institutions (Part-2), the use
cases (Expt-2), class diagram (Expt-3), sequence diagram (Expt-4) and application statechart / activity
diagram (Expt-5). The two modules below are the scope of the PBL prototype. Login (SRS 4.1), interview
scheduling, offer-letter documents, reports and the admin console are outside the scope; the web page lets
the tester choose the acting student, recruiter or placement officer instead of logging in.

Demo data (fictional): students 101 Aarav Kulkarni (CSE, 2023-2027, CGPA 8.60, 0 backlogs), 102 Diya Joshi
(IT, 7.40, 0), 103 Kabir Deshmukh (ECE, 6.80, 1), 104 Meera Patil (CSE, 9.10, 0, already placed), 105 Rohan
Wankhede (ME, 2022-2026, 7.90, 2). Recruiters 1 Ritika Menon (Nimbus Analytics, approved), 2 Sameer Khan
(Orbit Systems, approved), 3 Anil Rao (Vertex Labs, not approved). Placement officer 1 Dr. N. Bhagat.
Jobs: J-1 Software Engineer (published; CGPA ≥ 7.0, CSE/IT, 0 backlogs, batch 2023-2027), J-2 Embedded
Systems Engineer (published; CGPA ≥ 6.5, CSE/ECE/EE, ≤ 1 backlog), J-3 Data Analyst (pending; CGPA ≥ 7.5,
0 backlogs), J-4 Firmware Intern (published, deadline already passed; CGPA ≥ 6.0, ECE/EE).

## Module 1 – Job Posting and Eligibility Verification (SRS 4.3, 4.4; FR-09 to FR-14; UC-2)

| ID | Requirement |
|----|-------------|
| FR-1.1 | **Job posting (FR-10, UC-2).** A recruiter submits title (3–120 characters), description (20–2000), package/CTC in LPA (0 < CTC ≤ 100), location (2–80), application deadline (a date-time later than now) and eligibility criteria. Messages, checked in this order: `Title must be 3 to 120 characters.`, `Description must be 20 to 2000 characters.`, `Package (CTC) must be a positive number up to 100 LPA.` (a value that is not a number: `Package (CTC) must be a number.`), `Location is required (2 to 80 characters).`, `Deadline must be a future date and time.` A valid posting is stored as **Pending**, the placement officers are notified and the recruiter sees `Job J-<id> submitted for approval (status: Pending).` |
| FR-1.2 | **Eligibility rule-set (FR-13).** Each criterion is optional but at least one is required (`At least one eligibility criterion is required.`): minimum CGPA 0–10 (`Minimum CGPA must be between 0 and 10.`), allowed branches from CSE, IT, ECE, EE, ME, CE (`Allowed branches must be chosen from CSE, IT, ECE, EE, ME, CE.`), maximum active backlogs a whole number 0–10 (`Maximum backlogs must be a whole number from 0 to 10.`), batch in the form `YYYY-YYYY` spanning 4 years (`Batch must look like 2023-2027.`). A non-numeric CGPA/backlog value gives `<field> must be a number.` |
| FR-1.3 | **Company approval (FR-09).** A recruiter whose company is not approved by the placement cell cannot post: `403: Your company is not yet approved by the placement cell.` |
| FR-1.4 | **Job approval (FR-11, BR-02).** Only a placement officer may decide a posting (`403: Only a Placement Officer can approve or reject job postings.`). Decisions: approve → Published, reject → Rejected, return → Returned (`Decision must be approve, reject or return.`). Remarks of 5–200 characters are required to reject or return (`Remarks (5 to 200 characters) are required to reject or return a posting.`); remarks are optional on approval but at most 200 characters (`Remarks cannot exceed 200 characters.`). Only a Pending posting can be decided (`409: This job is not pending approval (status: <status>).`). A posting whose deadline has already passed cannot be approved (`409: The deadline of J-<id> has passed; return the posting so the recruiter can change it.`); it can still be rejected or returned. A posting is decided only once even when the same decision arrives several times at the same moment (double click, two officers). The recruiter is notified of every decision. On approval every eligible student who is not yet placed is notified and the officer sees `Job J-<id> published. <n> eligible student(s) notified.`; otherwise `Job J-<id> rejected. Recruiter notified.` / `Job J-<id> returned to the recruiter for changes.` |
| FR-1.5 | **Resubmission of a returned posting (UC-2 A1).** The recruiter who posted a Returned job can edit it (same validation as FR-1.1/1.2) and resubmit it; it becomes Pending again and the officers are notified: `Job J-<id> resubmitted for approval (status: Pending).` Other recruiters: `403: You can edit only your own job postings.`; a job that is not Returned: `409: Only a posting returned for changes can be edited (status: <status>).` |
| FR-1.6 | **Job search and filter (FR-12).** Students see only Published jobs. Filters: keyword (case-insensitive, in title, description or company), location (case-insensitive, contains), minimum package (`400: Minimum package must be a number.`) and "eligible only". Open jobs are listed first (earliest deadline first), then jobs whose deadline has passed, which are marked **Closed**. Results are paginated, 10 per page by default (`Page must be a whole number of at least 1.`). |
| FR-1.7 | **Automatic eligibility check (FR-14, BR-03).** A student is eligible for a job when CGPA ≥ minimum, branch is allowed, active backlogs ≤ maximum and batch matches; criteria not set are not checked. Each unmet criterion gives a reason: `CGPA <x> is below the minimum <y>.`, `Branch <b> is not in the allowed branches (<list>).`, `Active backlogs <n> exceed the maximum <m>.`, `Batch <b> does not match the required batch <r>.` (CGPA shown with 2 decimals). Every check is recorded in the eligibility table. |
| FR-1.8 | **Job board UI (SRS 4.4.2).** For a job the student is not eligible for, the board shows **Not eligible** with the unmet criteria and the Apply action is disabled; it is also disabled for a Closed job. |

## Module 2 – Job Application and Tracking (SRS 4.5; FR-15 to FR-17; UC-1; Expt-5 statechart)

| ID | Requirement |
|----|-------------|
| FR-2.1 | **Application submission (FR-15, UC-1).** The checks are made in this order: the job is Published (`409: Job J-<id> is not open for applications.`), the deadline has not passed (BR-04, `409: The application deadline for J-<id> has passed.`), the student is not already placed (BR-05 single-offer policy, `409: You are already placed; the placement policy blocks further applications.`), the student is eligible (E1, `409: You are not eligible for J-<id>: <reasons>`), no earlier application to the same job (E3, `409: You have already applied to J-<id> (tracking id <tid>).`), the resume belongs to the student and is active (`400: Select one of your active resumes.`), the optional cover note is at most 500 characters (`400: Cover note cannot exceed 500 characters.`). |
| FR-2.2 | **On success (UC-1 step 6–7)** the application is stored with status **Applied** and a unique tracking id `USPS-<YY>-<NNNN>` (2-digit year, 4-digit application number), the recruiter is notified, a confirmation notification goes to the student and the page shows `Application submitted for J-<id>. Tracking id <tid>.` |
| FR-2.3 | **Apply form (UC-1 step 4, E1, E2).** The student's active resume is pre-selected; inactive resumes are labelled `(inactive)`. When the selected job is one the student is not eligible for, the unmet criteria are listed and Submit is disabled; for a Closed job the form shows `The application deadline for J-<id> has passed.` and Submit is disabled. |
| FR-2.4 | **Persistence error (UC-1 E4).** If saving fails, the whole transaction is rolled back (no application, history or notification row remains) and the student sees `500: Your application could not be saved and nothing was stored. Please try again.` |
| FR-2.5 | **Status workflow (Expt-5 statechart, BR-08).** Applied –under_review→ Under Review –shortlist→ Shortlisted –schedule_interview→ Interview Scheduled (–reschedule→ itself) –interview_result→ Selected –offer_letter→ Offer Issued –accept_offer→ Accepted; reject from Under Review, Shortlisted, Interview Scheduled or Selected → Rejected; reject_offer from Offer Issued → Rejected; withdraw from Applied → Withdrawn. Any other event: `409: Event '<event>' is not allowed when the application is <state>.` (so an offer can only follow selection, BR-08); an event name that does not exist: `400: Unknown event '<event>'.` Each change is stored in the history with the actor and time, the student is notified, and the page shows `Application <tid> is now <state>.` A step is applied only once even when the same request arrives several times at the same moment; the extra requests get the 409 message of the new state. |
| FR-2.6 | **Who may change an application (BR-07).** Recruiter steps can be done only by the recruiter who posted the job or by a placement officer (`403: Only the recruiter who posted this job or a Placement Officer can update this application.`); accepting or declining an offer only by the student who applied (`403: Only the student who applied can respond to the offer.`). A recruiter's applicant list contains only applications to that recruiter's own jobs. |
| FR-2.7 | **Withdrawal (FR-16).** Only the student who applied (`403: Only the student who applied can withdraw this application.`), only while the application is Applied (`409: Only an application in the Applied state can be withdrawn (current: <state>).`) and only before the job deadline (`409: The deadline has passed; the application can no longer be withdrawn.`). |
| FR-2.8 | **Offer acceptance (BR-01, BR-05).** Accepting an offer marks the student Placed. A student who already holds an accepted offer cannot accept another (`409: You already hold an accepted offer; the placement policy allows only one.`) and cannot apply to further jobs (FR-2.1). |
| FR-2.9 | **Tracking (FR-17).** The student sees all own applications (newest first) with status, and a timeline of each: the main path Applied → … → Accepted with the reached and current states highlighted, Rejected/Withdrawn shown as an end state, and the full history (time, from → to, step, actor). |
| FR-2.10 | **Confirmation (SRS 3.1, destructive actions).** Withdraw, decline offer, reject an applicant and reject a posting ask for confirmation; cancelling leaves the record unchanged. |
| FR-2.11 | **Notifications (FR-25).** Each user sees own notifications, newest first, with time. |
| FR-2.12 | **Real-time updates (FR-17 "real-time", SRS 4.3.2).** Every open page shows changes made by any other user within about 2 seconds without reloading: a posted job appears in the officers' pending list, an approved job on the students' job board, a new application in the recruiter's applicant list and a status change in the student's applications. A notification that arrives this way also pops up on the page. A half-filled form is not cleared by such an update. |

> Changes after exploratory testing (run 2): the deadline rule for approval in FR-1.4 and the "only once" rules in
> FR-1.4 and FR-2.5 were added after BUG-02, BUG-03 and BUG-04 were found; test cases TC_M1_60, TC_M1_61,
> TC_INT_10 and TC_INT_11 were written for them.

## Non-functional points checked in the prototype

* All input is validated on the server (SRS 5.x Data Validation); the page never relies on browser-only checks.
* The business logic of both modules (`app/rules.py`) is free of HTTP and SQL so it is unit-tested directly.
* Responsive layout down to phone width (NFR-18).
